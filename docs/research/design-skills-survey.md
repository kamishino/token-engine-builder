# Design-skills survey: Superdesign, Better Design, design-taste, Canvas UI

Comparative architecture study of four design-related GitHub repos, read from primary sources (each repo's own files via `github.com` / `api.github.com` / `raw.githubusercontent.com`, plus the Agent Skills specification) on 2026-10-17, for token-engine-builder (colocated `src/skills/<skill>` → Vite-bundled `dist/<skill>` packages for a 3-tier DTCG token pipeline, per [../../ARCHITECTURE.md](../../ARCHITECTURE.md)). Neutral observations only. Prior frames are reused, not re-derived: categorization axes (Pocock lifecycle buckets vs Stitch installable plugins vs a flat pipeline) and the three style-detection approaches — **A. Interview-first**, **B. Extraction-first**, **C. Palette-mapping** — come from [skill-categorization-and-style-detection.md](./skill-categorization-and-style-detection.md); the Pocock/Stitch architecture background comes from [matt-pocock-skills-architecture.md](./matt-pocock-skills-architecture.md), [stitch-skills-architecture.md](./stitch-skills-architecture.md), and [skills-architecture-comparison.md](./skills-architecture-comparison.md).

Two of the four repos are not Agent Skills repos at all; they are covered for what they actually are, with only their design-system/token-relevant mechanics described, and skill-specific axes marked N/A rather than forced.

**Scope limits.** Server-side products that these repos point at but do not contain — the Superdesign web app and the separate `superdesign-skill` repo linked from Superdesign's README, and Better Design's hosted MCP server — were not surveyed as code. Claims about them below are limited to the client-visible contracts written inside the surveyed repos' own files, and are attributed as such.

**Spec baseline for verdicts.** The [Agent Skills specification](https://agentskills.io/specification) requires: `name` 1–64 chars, unicode lowercase alphanumeric + hyphens only, no leading/trailing or consecutive hyphens, and it **must match the parent directory name**; `description` 1–1024 chars, non-empty, describing what + when; optional `license`, `compatibility` (≤500 chars), `metadata` (string→string map, the spec's extension point), and `allowed-tools`. A skill is a directory with `SKILL.md` minimum and conventional optional `scripts/`, `references/`, `assets/`; the spec recommends `SKILL.md` under 500 lines. Description lengths below were measured from the parsed YAML frontmatter of each `SKILL.md` (block scalars unfolded), not estimated from file size.

## 1. superdesigndev/superdesign

### 1.1 What it is

An open-source **VS Code extension** (2025) that embeds an AI design agent in the IDE: a chat sidebar and an infinite-canvas webview where the agent generates single-screen HTML designs, themes, and wireframes from prompts, saving iterations as files the user forks and edits ([README.md](https://raw.githubusercontent.com/superdesigndev/superdesign/main/README.md)). The README states this repo is "the original open-source Superdesign IDE extension (2025)", is "no longer actively maintained", that the product "is now a web app", and that users who prefer their editor can drive Superdesign "as a design skill from coding agents like Claude Code and Cursor" via a different repo, `superdesigndev/superdesign-skill` ([README.md](https://raw.githubusercontent.com/superdesigndev/superdesign/main/README.md)). That sibling skill repo is a pointer in this repo's README, not part of this repo. **This repo contains no `SKILL.md` and is not an Agent Skills repo** (full recursive tree: [api.github.com tree](https://api.github.com/repos/superdesigndev/superdesign/git/trees/main?recursive=1)).

### 1.2 Layout + SKILL.md anatomy / spec compliance

Layout is a conventional extension split by code layer, per the tree and [package.json](https://raw.githubusercontent.com/superdesigndev/superdesign/main/package.json): `src/extension.ts` (activation, commands, project initialization), `src/providers/` (chat sidebar, Claude API / Claude Code LLM providers), `src/services/customAgentService.ts` (the built-in agent loop and system prompt), `src/tools/` (agent tools: read, write, edit, multiedit, bash, glob, grep, ls, theme), `src/webview/` (React canvas + chat UI), plus a root `system-prompt.txt` (a shorter alternate prompt) and `.cursor/rules/`. The extension contributes commands, an activity-bar webview, and configuration (`superdesign.llmProvider`, API keys, model enums) under VS Code engine `^1.90.0`, `main: ./dist/extension.js` ([package.json](https://raw.githubusercontent.com/superdesigndev/superdesign/main/package.json)).

**Spec verdict: N/A** — there is no skill directory, no YAML frontmatter, and nothing for the name/description rules to apply to. The closest analogue to a "skill instruction file" is prompt text embedded in TypeScript, plus rule files the extension writes into user projects (see §1.4).

### 1.3 Categorization axis

N/A for skills. Internally, code is categorized by **extension layer** (providers / services / tools / webview), and generated output is categorized by artifact kind in the user's project: designs and theme CSS under `.superdesign/design_iterations/`, uploaded reference images under `.superdesign/moodboard/` ([src/extension.ts](https://raw.githubusercontent.com/superdesigndev/superdesign/main/src/extension.ts), [src/services/customAgentService.ts](https://raw.githubusercontent.com/superdesigndev/superdesign/main/src/services/customAgentService.ts)). Neither resembles the lifecycle-bucket axis nor the plugin/audience axis from [skill-categorization-and-style-detection.md](./skill-categorization-and-style-detection.md).

### 1.4 Style detection approach — new variant: **staged-confirmation generation**

Taste is neither interviewed up front (A), extracted from an existing product (B), nor mapped from adjectives by a fixed table (C). The agent's system prompt mandates a sequential workflow in which it *proposes* style stage by stage and the user signs off each stage before the next begins:

1. **Layout design** — presented as an ASCII wireframe;
2. **Theme design** (color, font, spacing, shadow) — via the `generateTheme` tool, saved as a CSS file;
3. **Core animation design**;
4. **Generate** one HTML file per component, combined into a single HTML file referencing the theme CSS;
5. "You HAVE TO confirm with user step by step, don't do theme design until user sign off the layout design, same for all follownig steps" ([src/services/customAgentService.ts](https://raw.githubusercontent.com/superdesigndev/superdesign/main/src/services/customAgentService.ts)).

This is named here **staged-confirmation generation**: the style decision surface is a sequence of agent proposals with human approval gates, not an up-front question batch or a measurement of existing code. Three supporting mechanisms sit around it:

- **Fixed house constraints in the prompt**: Flowbite as base unless specified, avoid indigo/blue and "bootstrap style blue" unless requested, mandatory responsive output, a fixed Google-Font candidate list, `!important` on properties Tailwind/Flowbite might overwrite ([src/services/customAgentService.ts](https://raw.githubusercontent.com/superdesigndev/superdesign/main/src/services/customAgentService.ts)). The root `system-prompt.txt` variant adds different house rules: Tailwind via CDN, text only black or white, a 4pt-or-8pt spacing system with exact multiples, "elegant minimalism", and three parallel sub-agents producing design variations ([system-prompt.txt](https://raw.githubusercontent.com/superdesigndev/superdesign/main/system-prompt.txt)).
- **A palette-mapping (C) fragment**: two complete example theme blocks embedded verbatim in the prompt — `<neo-brutalism-style>` ("90s web design") and `<modern-dark-mode-style>` ("like vercel, linear") — each a full `:root` of OKLCH semantic variables the model is told to pattern from ([src/services/customAgentService.ts](https://raw.githubusercontent.com/superdesigndev/superdesign/main/src/services/customAgentService.ts)).
- **Rule-file seeding (project initialization)**: the `superdesign.initializeProject` command creates `.superdesign/design_iterations/`, seeds a `default_ui_darkmode.css` stylesheet there, and appends the same design-rule content to `.cursor/rules/design.mdc`, `CLAUDE.md`, and `.windsurfrules` so external coding agents follow the identical workflow and output folder ([src/extension.ts](https://raw.githubusercontent.com/superdesigndev/superdesign/main/src/extension.ts)). Moodboard images uploaded in chat are saved to `.superdesign/moodboard/` as design inputs ([src/extension.ts](https://raw.githubusercontent.com/superdesigndev/superdesign/main/src/extension.ts)); no code-extraction procedure (B) is present.

### 1.5 Executable layer

Fully executable TypeScript: the agent loop streams via the Vercel AI SDK (`ai`, `@ai-sdk/anthropic`, `@ai-sdk/openai`, `@ai-sdk/google`, `@openrouter/ai-sdk-provider`) with a local Claude Code binary as an alternative provider, and a Zod-validated tool set (read/write/edit/multiedit/bash/glob/grep/ls/theme) scoped to the workspace ([package.json](https://raw.githubusercontent.com/superdesigndev/superdesign/main/package.json), [src/services/customAgentService.ts](https://raw.githubusercontent.com/superdesigndev/superdesign/main/src/services/customAgentService.ts), [src/tools/theme-tool.ts](https://raw.githubusercontent.com/superdesigndev/superdesign/main/src/tools/theme-tool.ts)). Build is two esbuild contexts — extension host to `dist/extension.js` (CJS, Node, `vscode` external) and webview to `dist/webview.js` (ESM, browser) — after which the build copies `node_modules/@anthropic-ai/claude-code` and `src/assets` into `dist/` for runtime access ([esbuild.js](https://raw.githubusercontent.com/superdesigndev/superdesign/main/esbuild.js)). The theme tool itself only validates the path and writes the model-supplied CSS string to disk; it performs no color computation ([src/tools/theme-tool.ts](https://raw.githubusercontent.com/superdesigndev/superdesign/main/src/tools/theme-tool.ts)). The webview parses theme CSS with regexes for preview ([src/webview/utils/themeParser.ts](https://raw.githubusercontent.com/superdesigndev/superdesign/main/src/webview/utils/themeParser.ts)).

### 1.6 Distribution + versioning

Distributed as an editor extension: `package.json` is `superdesign-official` version `0.0.14`, publisher `SuperdesignDev` ([package.json](https://raw.githubusercontent.com/superdesigndev/superdesign/main/package.json)); the README's getting-started route is install from the Cursor/VS Code Marketplace ([README.md](https://raw.githubusercontent.com/superdesigndev/superdesign/main/README.md)). Publishing is tag-driven: pushing a `v*` tag runs `vsce publish` (Visual Studio Marketplace) and `ovsx publish` (Open VSX) in GitHub Actions ([.github/workflows/publish.yml](https://raw.githubusercontent.com/superdesigndev/superdesign/main/.github/workflows/publish.yml)); tags such as `v0.0.13`/`v0.0.12` exist with no GitHub Releases ([tags API](https://api.github.com/repos/superdesigndev/superdesign/tags?per_page=5), [releases API](https://api.github.com/repos/superdesigndev/superdesign/releases?per_page=3)). The hand-written [CHANGELOG.md](https://raw.githubusercontent.com/superdesigndev/superdesign/main/CHANGELOG.md) stops at `[0.0.8] - 2025-07-01`, six patch versions behind `package.json`'s `0.0.14`. License file is AGPLv3 with a carve-out: files marked `/* @license Enterprise */` sit under separate commercial terms ([LICENSE](https://raw.githubusercontent.com/superdesigndev/superdesign/main/LICENSE)).

### 1.7 Design-token relevance

Token format is a **single flat layer of shadcn-style semantic CSS custom properties**; there is no DTCG JSON, no primitive tier, no alias chain, and no ramp generation or contrast audit anywhere in the repo. The `generateTheme` tool's schema *requires* the model to emit a `:root` block containing `--background`/`--foreground`, `--primary`/`--secondary`/`--muted`/`--accent`, `--destructive`/`--border`/`--input`/`--ring`, `--card`/`--popover` + foregrounds, `--chart-1`…`--chart-5`, `--sidebar-*`, `--font-sans`/`--font-serif`/`--font-mono`, `--radius`, `--spacing`, and `--shadow-*` ([src/tools/theme-tool.ts](https://raw.githubusercontent.com/superdesigndev/superdesign/main/src/tools/theme-tool.ts)). The parser recognizes exactly `:root` (light) and an optional `.dark` block, mapping variables into a typed `ThemeColors` record with hard fallbacks (`'white'`, `'blue'`, …), plus fonts, `--radius`, `--spacing`, and `--shadow-*` extraction ([src/webview/utils/themeParser.ts](https://raw.githubusercontent.com/superdesigndev/superdesign/main/src/webview/utils/themeParser.ts)). Color space in the embedded examples is **OKLCH** (e.g. `--primary: oklch(0.6489 0.2370 26.9728)`) with `hsl()` shadows ([src/services/customAgentService.ts](https://raw.githubusercontent.com/superdesigndev/superdesign/main/src/services/customAgentService.ts)); the seeded `default_ui_darkmode.css` adds flat `--spacing-*` and `--font-size-*` scales on the same semantic variables ([src/extension.ts](https://raw.githubusercontent.com/superdesigndev/superdesign/main/src/extension.ts)). Tier structure relative to a 3-tier DTCG pipeline: semantic-only, values written directly on role names by the model, radius steps derived by `calc(var(--radius) ± …)` in examples. Generated designs style with Tailwind/Flowbite CDNs referencing the theme CSS file ([src/services/customAgentService.ts](https://raw.githubusercontent.com/superdesigndev/superdesign/main/src/services/customAgentService.ts)).

## 2. marvkr/better-design

### 2.1 What it is

A **hybrid of three things in one repo**: (a) a catalog of 31 curated design systems for shadcn/ui, each shipping a token stylesheet plus per-theme component overrides and shadcn registry JSON; (b) exactly **one first-party Agent Skill**, `skills/better-design/`, which is a thin workflow layer that delegates all design knowledge to a hosted MCP server; and (c) a vendored third-party skill, `animate-text`, installed under `.agents/skills/` and pinned by hash from another repo. The README describes the product as "a design MCP server, AI design-system registry, and UI review layer" giving agents "design tokens, component code, UI principles, icon direction, accessibility checks, and visual-design review rules" ([README.md](https://raw.githubusercontent.com/marvkr/better-design/main/README.md)). The MCP server's own code is **not in this repo**: the recursive tree contains no root `package.json` or server directory (top level is `.agents/`, `components/`, `registry/`, `scripts/`, `skills/`, `tests/`, `skills-lock.json`) ([api.github.com tree](https://api.github.com/repos/marvkr/better-design/git/trees/main?recursive=1)), and the skill's Codex sidecar points at the hosted endpoint `https://better-design.com/api/mcp` with `transport: streamable_http` ([skills/better-design/agents/openai.yaml](https://raw.githubusercontent.com/marvkr/better-design/main/skills/better-design/agents/openai.yaml)).

### 2.2 Layout + SKILL.md anatomy / spec compliance

Layout, per the README's own structure diagram and the tree ([README.md](https://raw.githubusercontent.com/marvkr/better-design/main/README.md), [api.github.com tree](https://api.github.com/repos/marvkr/better-design/git/trees/main?recursive=1)):

```
components/<system>/   # 31 systems: globals.css + components/ui/*.tsx overrides + lib/
registry/<system>/     # per-component shadcn registry JSON + index.json; registry/registry.json at root
scripts/               # maintainer generators (registry index, transitions fan-out, installers)
skills/better-design/  # the installable first-party skill: SKILL.md + agents/openai.yaml
.agents/skills/        # "Other installed agent skills" — vendored animate-text
tests/                 # vitest/bun tests for the shared transition components
```

`skills/better-design/SKILL.md` (58 lines) has minimal frontmatter — only `name` and `description` — and a body organized as Connect → trust boundaries → interface workflow → new-build flow → specialist guidance → "Keep the MCP authoritative" ([skills/better-design/SKILL.md](https://raw.githubusercontent.com/marvkr/better-design/main/skills/better-design/SKILL.md)). Its defining instruction is delegation: "Use Better Design MCP tools as the source of design guidance. Keep this skill as the workflow layer; retrieve the current principles, systems, components, and review rules from the MCP instead of replacing them with generic static advice", and if the MCP tools are unavailable the agent must say so, link the setup docs, and stop — "Never claim that Better Design guidance was loaded or reviewed when the MCP tools were unavailable" ([skills/better-design/SKILL.md](https://raw.githubusercontent.com/marvkr/better-design/main/skills/better-design/SKILL.md)). The `agents/openai.yaml` sidecar declares the MCP dependency (`type: mcp`, `value: better-design`, hosted URL) and a default prompt ([skills/better-design/agents/openai.yaml](https://raw.githubusercontent.com/marvkr/better-design/main/skills/better-design/agents/openai.yaml)).

**Spec verdict (first-party skill): PASS on the checked constraints.** `name: better-design` is lowercase-hyphen charset, ≤64 chars, and matches its parent directory `skills/better-design/`; `description` measures 369 chars (≤1024), non-empty, stating what + when ("Build, improve, and review production interfaces with the Better Design MCP. Use for frontend design, UI, UX, …") ([skills/better-design/SKILL.md](https://raw.githubusercontent.com/marvkr/better-design/main/skills/better-design/SKILL.md), spec limits per [agentskills.io/specification](https://agentskills.io/specification)). No optional fields (`license`, `compatibility`, `metadata`, `allowed-tools`) are used; the skill ships no `scripts/`/`references/`/`assets/` — by design, since content is fetched from the MCP at runtime.

The vendored `.agents/skills/animate-text/SKILL.md` (85 lines) also passes the same checks (`name: animate-text` matches its directory; description 333 chars) and is the repo's only example of the spec's canonical optional-directory anatomy: `scripts/*.mjs` helpers (`list-specs`, `get-spec`, `get-effect`, `find-spec`), `references/` (catalog, schema, selection guide, implementation notes), and `assets/` (`specs/*.json` portable motion contracts, `effects/*.json` exact recipes, catalog/presets), with JSON declared authoritative over prose on conflict ([.agents/skills/animate-text/SKILL.md](https://raw.githubusercontent.com/marvkr/better-design/main/.agents/skills/animate-text/SKILL.md)). Its provenance is recorded in [skills-lock.json](https://raw.githubusercontent.com/marvkr/better-design/main/skills-lock.json): `source: pixel-point/animate-text`, `skillPath: skills/animate-text/SKILL.md`, with a `computedHash` — i.e. an installed dependency, not first-party content of this repo.

One naming drift is observable between the two first-party documents: the README's tool table lists `resolve-design-system`, `get-design-system-docs`, `get-ui-principle`, `get-review-rules`, `resolve-icon-library`, `search-icons` ([README.md](https://raw.githubusercontent.com/marvkr/better-design/main/README.md)), while the SKILL.md body instructs calls to `find-design-system`, `get-design-system-kit`, `create-design-system`, `get-design-system-status`, `extract-design-system` / `extract-from-url`, `get-ux-principle`, `check-comprehension`, `review-ui-code`, `inspect-spacing`, `find-icon-library` / `find-icons` / `install-icons` ([skills/better-design/SKILL.md](https://raw.githubusercontent.com/marvkr/better-design/main/skills/better-design/SKILL.md)). Only `get-ui-principle` and `get-review-rules` appear in both.

### 2.3 Categorization axis

There is only one first-party skill, so there is no skill-grouping axis to compare against lifecycle buckets or plugins. What *is* categorized is the design-system catalog, on an **exemplar axis**: each system is an evocation of a known product or genre (Linear, Stripe, Vercel, Notion, Apple, Supabase, Figma, Airbnb, plus genre-named systems such as `cinematic-dark`, `tactile-minimal`), tabulated in the README by Theme (dark/light), Vibe, and Best For ([README.md](https://raw.githubusercontent.com/marvkr/better-design/main/README.md)). The machine-readable form of the same axis lives in each `registry/<system>/index.json` as `personality[]` and `industry[]` tag arrays — e.g. Linear: `personality: [minimal, clean, professional, focused, dark]`, `industry: [developer-tools, productivity, saas]`, alongside `componentCount` and the component list with registry dependencies ([registry/linear/index.json](https://raw.githubusercontent.com/marvkr/better-design/main/registry/linear/index.json)). Relative to the frames in [skill-categorization-and-style-detection.md](./skill-categorization-and-style-detection.md): the grouping unit is not a skill's ship-state (Pocock) or install audience (Stitch) but a **retrievable catalog entry keyed by product personality and industry**, existing so a brief can be matched to one whole prebuilt system (§2.4). The two skill directories that do exist are separated by **provenance/install route**, not topic: `skills/` for the installable first-party skill, `.agents/skills/` for "other installed agent skills" ([README.md](https://raw.githubusercontent.com/marvkr/better-design/main/README.md), [skills-lock.json](https://raw.githubusercontent.com/marvkr/better-design/main/skills-lock.json)).

### 2.4 Style detection approach — new variant: **exemplar-matching**, with B fragments

The primary mechanism for new work does not fit A/B/C as defined in [skill-categorization-and-style-detection.md](./skill-categorization-and-style-detection.md) and is named here **exemplar-matching (catalog retrieval at whole-system granularity)**: the agent calls `find-design-system` with the product and audience, shows "the strongest matches", and lets the user choose a starting point or a fully custom direction, then loads that system's install kit (`get-design-system-kit`, `react` target in coding agents / `html` in inline canvases) ([skills/better-design/SKILL.md](https://raw.githubusercontent.com/marvkr/better-design/main/skills/better-design/SKILL.md)). The README describes the same flow as semantic matching: `resolve-design-system("fintech dashboard, Stripe")` → load docs, CSS tokens, component code, icon library → "builds with semantic tokens instead of raw colors" ([README.md](https://raw.githubusercontent.com/marvkr/better-design/main/README.md)). Where palette-mapping (C) translates words into token values, exemplar-matching translates a brief into a *named, prebuilt design system* and adds a human choice gate among ranked matches; the match keys available in-repo are the `personality`/`industry` tags above, while the matching engine itself is server-side and not observable from this repo.

Around that core sit three further observed paths:

- **Extraction (B), server-side**: "When the user already has a brand source, call `extract-design-system` or `extract-from-url` before generating and pass the extracted token sheet through unchanged" ([skills/better-design/SKILL.md](https://raw.githubusercontent.com/marvkr/better-design/main/skills/better-design/SKILL.md)). The extraction implementation is not in the repo.
- **Extraction-as-preservation (B fragment, in-repo)**: for existing products the workflow's first steps are "Inspect the repository's framework, existing tokens, components, and local instructions before choosing a visual direction" and "Preserve an existing product's design system. Do not replace its brand merely because another catalog system looks relevant", with a matching prohibition on installing a catalog system into an established product unless asked ([skills/better-design/SKILL.md](https://raw.githubusercontent.com/marvkr/better-design/main/skills/better-design/SKILL.md)).
- **Hosted custom generation**: for a custom brand, `create-design-system` (with a chosen catalog base when applicable) returns a project URL and the agent polls `get-design-system-status` "until the install kit is ready" — an asynchronous server-side generation whose internals are not in the repo ([skills/better-design/SKILL.md](https://raw.githubusercontent.com/marvkr/better-design/main/skills/better-design/SKILL.md)).

Interview (A) is absent: the only human decision point specified is choosing among presented matches, with no question set. The always-on layer is not style detection but style *enforcement during and after* generation: load `get-ui-principle`/`get-ux-principle` before implementing, then `get-review-rules` + `check-comprehension` (and where available `review-ui-code`, `inspect-spacing` on a rendered DOM) after, fixing "all critical and serious findings before handoff" ([skills/better-design/SKILL.md](https://raw.githubusercontent.com/marvkr/better-design/main/skills/better-design/SKILL.md), [README.md](https://raw.githubusercontent.com/marvkr/better-design/main/README.md)).

### 2.5 Executable layer

The first-party skill contains **no executable code**; its executable layer is the hosted MCP server reached at runtime, whose implementation this repo does not contain (see §2.1). Executable code that *is* in the repo is maintainer/generator tooling in Node (`.mjs`, no bundling): `scripts/generate-transitions.mjs` fans 9 shared transition components from a single source directory (`scripts/transitions-src/`) out to every design system as byte-identical TSX copies with a "GENERATED FILE" banner plus registry JSON and a meta-entry, then regenerates the root registry index ([scripts/generate-transitions.mjs](https://raw.githubusercontent.com/marvkr/better-design/main/scripts/generate-transitions.mjs), [README.md](https://raw.githubusercontent.com/marvkr/better-design/main/README.md)); `scripts/generate-registry-json.mjs` builds the flat `registry/registry.json` discovery index (file `path`+`type` only, never `content`; intra-registry dependencies normalized to `<ds>/<component>`) ([scripts/generate-registry-json.mjs](https://raw.githubusercontent.com/marvkr/better-design/main/scripts/generate-registry-json.mjs)). The vendored animate-text skill's helpers are plain Node 20+ `.mjs` lookup scripts over its JSON assets, explicitly optional ("If Node is unavailable, the core skill still works through the Markdown references and JSON assets alone") ([.agents/skills/animate-text/SKILL.md](https://raw.githubusercontent.com/marvkr/better-design/main/.agents/skills/animate-text/SKILL.md)). Tests (vitest via bun, per the README's `cd tests && bun install && bun run test`) cover the transition components ([README.md](https://raw.githubusercontent.com/marvkr/better-design/main/README.md)). Nothing is compiled or bundled for distribution: registry JSON embeds component source as text for the shadcn CLI to copy into a user project (e.g. [registry/linear/globals.json](https://raw.githubusercontent.com/marvkr/better-design/main/registry/linear/globals.json)).

### 2.6 Distribution + versioning

Three distribution routes are documented in the README's Setup section ([README.md](https://raw.githubusercontent.com/marvkr/better-design/main/README.md)):

1. **Skill + installer**: `npx skills add marvkr/better-design --skill better-design` installs the skill, then `npx better-design` "detects your coding tools and connects the MCP without replacing their existing configuration. No account is required." The `better-design` npm package backing the second command is not present in this repo (no root `package.json` in the tree).
2. **Remote MCP manually**: add `https://better-design.com/api/mcp` with an `Authorization: Bearer` API key obtained from `better-design.com/settings` to any MCP client's config (Claude Desktop config shown explicitly).
3. **Components via shadcn registry**: `npx shadcn@latest add https://www.better-design.com/registry/<design-system>/<component>.json`, or through the `@better-design` namespace that `registry/registry.json` is generated to serve ([scripts/generate-registry-json.mjs](https://raw.githubusercontent.com/marvkr/better-design/main/scripts/generate-registry-json.mjs)).

**Versioning: none observable in-repo.** No git tags, no GitHub Releases, no changelog, no version field in the first-party skill's frontmatter, and no per-item versions in registry JSON ([tags API](https://api.github.com/repos/marvkr/better-design/tags?per_page=5), [releases API](https://api.github.com/repos/marvkr/better-design/releases?per_page=3), [skills/better-design/SKILL.md](https://raw.githubusercontent.com/marvkr/better-design/main/skills/better-design/SKILL.md)). The only pin in the repo is the vendored skill's `computedHash` in [skills-lock.json](https://raw.githubusercontent.com/marvkr/better-design/main/skills-lock.json) (`"version": 1` there is the lockfile schema version, not a product version). License is MIT ([README.md](https://raw.githubusercontent.com/marvkr/better-design/main/README.md)).

### 2.7 Design-token relevance

This repo has the largest concrete token surface of the four, in a **Tailwind v4 / shadcn CSS-variable format — not DTCG**. Each system's `globals.css` (e.g. [components/linear/globals.css](https://raw.githubusercontent.com/marvkr/better-design/main/components/linear/globals.css), [components/stripe/globals.css](https://raw.githubusercontent.com/marvkr/better-design/main/components/stripe/globals.css), [components/vercel/globals.css](https://raw.githubusercontent.com/marvkr/better-design/main/components/vercel/globals.css)) has the same three-part shape:

1. `:root { … }` — a fixed vocabulary of **semantic color variables with raw OKLCH values written directly on them** (`--background`, `--foreground`, `--card`, `--popover`, `--primary`, `--secondary`, `--muted`, `--accent`, `--destructive`, each + `-foreground`, `--border`, `--input`, `--ring`), plus a single `--radius` length. Color space is **OKLCH throughout** (e.g. Linear `--background: oklch(0.223 0.0183 279.84)`, `--primary: oklch(0.6317 0.1989 275.24)`; achromatic systems use chroma `0`, e.g. Vercel).
2. `@theme inline { … }` — a mechanical alias layer mapping Tailwind theme keys to those variables (`--color-primary: var(--primary)`, …) and deriving radius steps arithmetically (`--radius-sm: calc(var(--radius) - 4px)`, `-md` −2px, `-lg` = base, `-xl` +4px).
3. `@layer base` — `border-border outline-ring/50` on all elements and a **hardcoded per-system font stack** on `html` (Geist Sans var for Linear/Vercel, `"Sohne"` for Stripe), not a font token.

Tier structure relative to a 3-tier DTCG pipeline: there is **no primitive tier and no alias-only discipline** — semantic names carry literal values, Tailwind keys alias the semantics, and the third tier exists as *component code* rather than component tokens: per-system TSX overrides encode the distinguishing treatment directly (e.g. Linear's button derives its ring via `color-mix(in oklch, var(--primary) 55%, transparent)`, layered rgba shadows, gradient/hover recipes per variant) ([components/linear/components/ui/button.tsx](https://raw.githubusercontent.com/marvkr/better-design/main/components/linear/components/ui/button.tsx)). The README's contributing section states this as doctrine: "Design nuances live in the components, not just CSS variables — shadow layers, focus states, border thickness, hover transitions, and radius variations by context all need to be captured in component code" ([README.md](https://raw.githubusercontent.com/marvkr/better-design/main/README.md)). The registry form duplicates the same tokens twice: [registry/linear/globals.json](https://raw.githubusercontent.com/marvkr/better-design/main/registry/linear/globals.json) carries the full CSS as `files[].content` and again as a `cssVars: { light: {…} }` map — in the Linear (dark) system the dark values sit under the `light` key, i.e. each system ships a single fixed mode with no light/dark pair in that entry. No DTCG `$value`/`$type` structure, no ramp steps (50–950), no spacing/type scales as tokens, and no in-repo contrast/audit gate were found; accessibility and visual review are delegated to the hosted MCP's review tools (§2.4).

### 3.2 Layout + SKILL.md anatomy / spec compliance

### 3.4 Style detection approach — variant of C: **design-read inference**

The core skill's §0 "READ THE ROOM BEFORE ANYTHING" instructs the agent to infer, before writing code: (1) page kind, (2) "vibe words" from the brief, (3) audience ("the audience picks the aesthetic, not your taste"), and (4) existing brand as input for redesigns; then to **declare a one-line "design read"** before generating ("*Reading this as: B2B SaaS landing for technical buyers, Linear-style minimal…*"), and: "If the read is genuinely ambiguous, ask exactly one question. Otherwise proceed — do not default." ([skills/design-taste/SKILL.md](https://raw.githubusercontent.com/madebymustafa/design-taste/main/skills/design-taste/SKILL.md)).

Against Q2's three approaches in [skill-categorization-and-style-detection.md](./skill-categorization-and-style-detection.md): it is **palette-mapping (C) in mechanism** — words in the brief are translated into a direction at generation time with no human question batch and no product measurement — but with a distinct surface behavior that is named here **design-read inference**: the mapping's result must be *declared in one line before generation*, making the otherwise-silent table lookup an inspectable, vetoable statement, and the single-question fallback replaces interview (A) rather than implementing it. Interest lies in what is banned around it: §1's "NEVER LIST" enumerates the LLM defaults the inference must not collapse into (indigo-purple gradients, centered badge hero, three equal cards, Inter + `slate-900`, `rounded-2xl`, glassmorphism, emoji icons), and §7's pre-flight checklist fails output that "could have been made by typing 'landing page' into the same agent without this skill" ([skills/design-taste/SKILL.md](https://raw.githubusercontent.com/madebymustafa/design-taste/main/skills/design-taste/SKILL.md)).

Once a genre pack is selected — selection itself happening by description/trigger matching at load time, per "your agent picks what it needs from the description" ([README.md](https://raw.githubusercontent.com/madebymustafa/design-taste/main/README.md)) — detection ends: the pack *is* a precomputed mapping from identity name to a fixed palette/type/composition that is applied, not adapted ("Palette (Fixed)", "Typography (Fixed)", "Composition (Fixed)" in [skills/editorial-minimal/SKILL.md](https://raw.githubusercontent.com/madebymustafa/design-taste/main/skills/editorial-minimal/SKILL.md)). One extraction (B) fragment exists, inside a craft skill rather than the core: `taste-design-system` §3 prescribes an inventory audit of an existing codebase — list every hex, flag off-scale spacing, count type sizes, cluster radius/elevation values, list components — producing a token map and violation list, explicitly before building anything ([skills/taste-design-system/SKILL.md](https://raw.githubusercontent.com/madebymustafa/design-taste/main/skills/taste-design-system/SKILL.md)). The core skill's "existing brand" input (point 4 above) names brand artifacts as inputs but specifies no extraction procedure.

### 3.7 Design-token relevance

Tokens appear as **prose doctrine, not machine-readable artifacts**: there are no token files (DTCG JSON, CSS token sheets, or palette data) in the repo; concrete values live as literals inside `SKILL.md` bodies and the demo HTML ([api.github.com tree](https://api.github.com/repos/madebymustafa/design-taste/git/trees/main?recursive=1)). - **Color construction**: `taste-color` prescribes 60-30-10 palette architecture, ramp building in **OKLCH** ("Never interpolate between hex values blindly"; neutrals chroma near 0; accent hue locked, chroma peaking at 500–600), shipping hex computed from OKLCH where the stack requires it, WCAG 2.2 ratios (4.5:1 body, 3:1 large/UI/focus) computed rather than eyeballed, semantic names carrying jobs (`--color-danger-text` not `--color-red-700`), and colorblind-safe guidance (never red/green alone; Okabe-Ito for data viz) ([skills/taste-color/SKILL.md](https://raw.githubusercontent.com/madebymustafa/design-taste/main/skills/taste-color/SKILL.md)).
- **Genre palettes as fixed hex**: the packs themselves specify literals in **hex/rgba, not OKLCH** — e.g. editorial-minimal fixes paper `#F5F1EA`, ink `#1A1A18`, vermillion `#E34A2B`, hairlines `rgba(26,26,24,0.14)`, "No other colors. The corresponding demo carries them as CSS variables (`--paper`, `--ink`, `--accent`, `--hairline`) with hex values and zero `oklch()` occurrences, i.e. a two-name-layer (role-ish variable → literal) with no primitive ramp behind it ([examples/after.html](https://raw.githubusercontent.com/madebymustafa/design-taste/main/examples/after.html)); [docs/CONTRIBUTING.md](https://raw.githubusercontent.com/madebymustafa/design-taste/main/docs/CONTRIBUTING.md) requires exactly this "exact values" form ("Paper `#F5F1EA`… is executable").

There is no generator, audit script, or build step implementing any of the above; `taste-code-craft`'s "token-driven CSS (zero hardcoded values)" is likewise an instruction to the generating agent, checkable only by the checklist pass in prose ([README.md](https://raw.githubusercontent.com/madebymustafa/design-taste/main/README.md), [skills/taste-design-system/SKILL.md](https://raw.githubusercontent.com/madebymustafa/design-taste/main/skills/taste-design-system/SKILL.md)).

**Spec verdict: N/A** (no skills). Each effect is a vanilla TypeScript engine (raw WebGL2 + GLSL `#version 300 es` shaders; zero dependencies except `three` for object effects) plus a WGSL/vgpu twin with the same props and public API, wrapped by thin per-framework components ([README.md](https://raw.githubusercontent.com/DavidHDev/canvas-ui/main/README.md), [src/lib/Liquid/LiquidVanilla.ts](https://raw.githubusercontent.com/DavidHDev/canvas-ui/main/src/lib/Liquid/LiquidVanilla.ts), [src/lib/Liquid/Liquid.tsx](https://raw.githubusercontent.com/DavidHDev/canvas-ui/main/src/lib/Liquid/Liquid.tsx)). The React wrapper pattern is representative: feature-detect `supportsHtmlInCanvas`, mount the engine over source/output canvases, forward live option updates via `setOptions`, destroy on unmount, and render plain children when unsupported ([src/lib/Liquid/Liquid.tsx](https://raw.githubusercontent.com/DavidHDev/canvas-ui/main/src/lib/Liquid/Liquid.tsx)). Repo-internal generation runs as unbundled Node type-stripping scripts (`node --experimental-strip-types`): `scripts/build-registry.mts` writes `public/r/*.json` + `registry.json` (generated at `dev`/`prebuild`, not committed), and `scripts/build-live-wrappers.mts` source-transforms React wrappers into docs-site versions that can switch WebGL/WebGPU engines at runtime ([package.json](https://raw.githubusercontent.com/DavidHDev/canvas-ui/main/package.json), [scripts/build-registry.mts](https://raw.githubusercontent.com/DavidHDev/canvas-ui/main/scripts/build-registry.mts), [scripts/build-live-wrappers.mts](https://raw.githubusercontent.com/DavidHDev/canvas-ui/main/scripts/build-live-wrappers.mts)). CI runs `tsc --noEmit`, eslint, and a full build on push/PR ([.github/workflows/ci.yml](https://raw.githubusercontent.com/DavidHDev/canvas-ui/main/.github/workflows/ci.yml)); `scripts/test-*.mjs` hold targeted behavior tests (bounded inputs, canvas viewport, html-in-canvas, WebGPU resize, particle-scroll fallback) ([api.github.com tree](https://api.github.com/repos/DavidHDev/canvas-ui/git/trees/main?recursive=1)).

### 4.6 Distribution + versioning

Distribution is the shadcn registry under the trusted `@canvas-ui` namespace: `npx shadcn@latest add @canvas-ui/liquid-react` (swap component/framework; append `-webgpu` for the WebGPU build), landing editable source in `components/canvasui/` — "Copy, do not install" ([README.md](https://raw.githubusercontent.com/DavidHDev/canvas-ui/main/README.md), [public/llms.txt](https://raw.githubusercontent.com/DavidHDev/canvas-ui/main/public/llms.txt)). The namespace can optionally be pinned in a consumer's `components.json` registries map; the repo's own [components.json](https://raw.githubusercontent.com/DavidHDev/canvas-ui/main/components.json) configures its docs site (style `base-nova`, baseColor `neutral`, `cssVariables: true`) with an empty `registries` object. Agent-driven installation uses **shadcn's** MCP server, not a Canvas UI server: `npx shadcn@latest mcp init --client claude|cursor|vscode|opencode`, or a `[mcp_servers.shadcn]` entry in `~/.codex/config.toml`, after which prompts like "Add liquid from the @canvas-ui registry to my hero section" work through the registry ([src/app/(shell)/docs/mcp/page.tsx](https://raw.githubusercontent.com/DavidHDev/canvas-ui/main/src/app/(shell)/docs/mcp/page.tsx)). **Versioning: effectively none for consumers** — the repo `package.json` is `private: true`, version `0.1.0`, naming the docs-site app rather than a published library package ([package.json](https://raw.githubusercontent.com/DavidHDev/canvas-ui/main/package.json)); there are no git tags, GitHub Releases, or changelog ([tags API](https://api.github.com/repos/DavidHDev/canvas-ui/tags?per_page=5), [releases API](https://api.github.com/repos/DavidHDev/canvas-ui/releases?per_page=3)); generated registry items emit `dependencies`/`devDependencies` but no per-item version field ([src/lib/registry.ts](https://raw.githubusercontent.com/DavidHDev/canvas-ui/main/src/lib/registry.ts), [scripts/build-registry.mts](https://raw.githubusercontent.com/DavidHDev/canvas-ui/main/scripts/build-registry.mts)). License is MIT + Commons Clause: free in products, but selling/redistributing the components themselves is barred ([LICENSE.md](https://raw.githubusercontent.com/DavidHDev/canvas-ui/main/LICENSE.md)).

### 4.7 Design-token relevance

The library components expose **no design-token interface**: effect configuration is typed numeric simulation props, not CSS variables or token files. `LiquidOptions` is representative — `simResolution`, `dyeResolution`, dissipation/pressure/curl/radius/force/distortion numbers, and `color?: [number, number, number]` documented as "Trail color as [r, g, b] in 0-1 range" (sRGB triples, linearized in-shader via an sRGB→linear transfer for rendering), default `[0.145, 0.239, 0.867]` ([src/lib/Liquid/LiquidVanilla.ts](https://raw.githubusercontent.com/DavidHDev/canvas-ui/main/src/lib/Liquid/LiquidVanilla.ts)). The README states the architectural reason: "Nothing depends on another Canvas UI component, and each engine defines its own props" ([README.md](https://raw.githubusercontent.com/DavidHDev/canvas-ui/main/README.md)). Effects are also token-agnostic by construction: they capture and redraw whatever the host page's own CSS produced, so the host's token system passes through untouched ([README.md](https://raw.githubusercontent.com/DavidHDev/canvas-ui/main/README.md)); one catalog description claims theme-awareness at the effect level (`Clouds`: "Theme-aware mist") without a token contract being named ([public/llms.txt](https://raw.githubusercontent.com/DavidHDev/canvas-ui/main/public/llms.txt), [src/data/components.ts](https://raw.githubusercontent.com/DavidHDev/canvas-ui/main/src/data/components.ts)).

The only token-shaped artifact in the repo is the **docs site's own theme**, [src/app/globals.css](https://raw.githubusercontent.com/DavidHDev/canvas-ui/main/src/app/globals.css): a stock Tailwind v4/shadcn arrangement (`@import "shadcn/tailwind.css"`) in which `:root` and `.dark` blocks hold the full semantic vocabulary (`--background`…`--ring`, `--chart-1`…`5`, `--sidebar-*`, `--radius: 0.625rem`) as **OKLCH values that are almost entirely achromatic** (chroma `0`; exceptions are `--destructive` and dark-mode `--sidebar-primary`), and `@theme inline` mechanically aliases `--color-*` theme keys to those variables with radius steps as multipliers of `--radius` (0.6×/0.8×/1×/1.4×/1.8×/2.2×/2.6×). Tier structure: the same semantic-only, single-layer shape as §1.7/§2.7, scoped to the site chrome; there is no primitive tier, no DTCG, and no token generation or audit code in the repo.
