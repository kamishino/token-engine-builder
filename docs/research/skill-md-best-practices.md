# SKILL.md content-structure best practices (Agent Skills official docs)

Distillation of the AGENT-friendly SKILL.md authoring rules from the official Agent Skills docs (agentskills.io). Each practice states the rule, why it matters for agents as the docs explain it, and — clearly marked — the researcher's observation on how our 4 pipeline skills (`src/skills/*/SKILL.md`) stand against it.

## 1. Frontmatter rules

**Rule.** `SKILL.md` must open with YAML frontmatter; `name` (1–64 chars, lowercase alphanumerics + hyphens, no leading/trailing/consecutive hyphens) and non-empty `description` (1–1024 chars) are required; `license`, `compatibility` (≤500 chars, only when the skill has real environment requirements), `metadata` (string→string map), and `allowed-tools` are optional. `name` must match the parent directory name ([spec frontmatter](https://agentskills.io/specification#frontmatter), [name field](https://agentskills.io/specification#name-field), [description field](https://agentskills.io/specification#description-field), [compatibility](https://agentskills.io/specification#compatibility-field), [allowed-tools](https://agentskills.io/specification#allowed-tools-field)). `allowed-tools` is specified as a **space-separated string** of pre-approved tools and is experimental — support varies by agent ([allowed-tools](https://agentskills.io/specification#allowed-tools-field)). Validate with `skills-ref validate ./my-skill` ([validation](https://agentskills.io/specification#validation)).

**Why it matters.** `name` + `description` are the only tokens loaded for every skill at startup, so they carry the entire discovery/trigger burden; everything else loads only on activation ([progressive disclosure](https://agentskills.io/specification#progressive-disclosure), [how triggering works](https://agentskills.io/skill-creation/optimizing-descriptions#how-skill-triggering-works)).

**[Researcher's observation.]** All 4 skills comply on `name` (kebab-case, matches directory) and carry `license: MIT` + `compatibility: Node.js >=22.12`. One deviation: `allowed-tools` is written as a YAML list (`- Bash` / `- Read` …) while the spec defines it as a space-separated string (e.g. `allowed-tools: Bash(git:*) Bash(jq:*) Read`); worth normalising or confirming harness tolerance.

## 2. Description trigger-phrasing

**Rule.** The `description` must say what the skill does **and when to use it**, with concrete keywords; the canonical good example names capabilities plus trigger contexts ("Extracts text and tables from PDF files… Use when working with PDF documents or when the user mentions PDFs, forms, or document extraction") versus the poor "Helps with PDFs" ([description field](https://agentskills.io/specification#description-field)). The optimizing-descriptions guide adds: use **imperative phrasing** ("Use this skill when…", not "This skill does…"); focus on **user intent, not implementation**; **err on the side of being pushy** by listing contexts including ones where the user doesn't name the domain ("even if they don't explicitly mention 'CSV'"); keep it to a few sentences — long enough to cover scope, short enough not to bloat context across many skills, hard cap 1024 chars ([writing effective descriptions](https://agentskills.io/skill-creation/optimizing-descriptions#writing-effective-descriptions), [applying the result](https://agentskills.io/skill-creation/optimizing-descriptions#applying-the-result)).

**Why it matters.** The agent matches the description against what the user asked for; under-specified descriptions don't trigger, over-broad ones false-trigger. Nuance: agents usually consult skills only for tasks needing beyond-baseline knowledge (unfamiliar API, domain workflow, uncommon format), so the description must surface the specialised-knowledge angle ([how triggering works](https://agentskills.io/skill-creation/optimizing-descriptions#how-skill-triggering-works)).

**[Researcher's observation.]** All 4 descriptions already use the recommended imperative "Use when…" form with pipeline-position + trigger keywords ("starting a design system… no style-spec.json exists yet"; "after generating or editing tokens, before building"; "audit passes and CSS/Tailwind output is needed"; "spec exists and tokens/ is missing or the anchor changed") — this matches the good-example pattern. None has been trigger-eval tested per §9; that loop is the remaining gap.

## 3. Body organization: procedures over declarations

**Rule.** Teach the agent **how to approach a class of problems**, not what to produce for one instance: reusable method steps (read schema → join on convention → filter → aggregate) beat instance-specific answers (join these two tables, filter EMEA) ([favor procedures](https://agentskills.io/skill-creation/best-practices#favor-procedures-over-declarations)). Specific details are still welcome where they constrain output — format templates, hard constraints ("never output PII"), tool-specific instructions — but the _approach_ must generalise ([same](https://agentskills.io/skill-creation/best-practices#favor-procedures-over-declarations)). Recommended body sections: step-by-step instructions, input/output examples, common edge cases ([body content](https://agentskills.io/specification#body-content)).

**Why it matters.** A skill fires across many prompts; instance-specific instructions only help the exact task they were written for, while a method transfers. Constraints and templates, by contrast, reliably shape every run's output ([templates section](https://agentskills.io/skill-creation/best-practices#templates-for-output-format)).

**[Researcher's observation.]** All 4 bodies are procedural (numbered Steps with commands + done-gates) plus specific constraints where they matter (OKLCH-only, tier rules, exit-code gate, `oklch(` spot-checks). This matches the recommended mix; no body is an instance-specific answer.

## 4. Progressive disclosure and file references

**Rule.** Structure for three loading tiers: metadata (~100 tokens, always loaded) → instructions (<5000 tokens, loaded on activation) → resources (loaded only when required). Keep the core instructions agents need on every run in `SKILL.md`; move detailed reference to `references/` or similar, and crucially tell the agent **when** to load each file ("Read `references/api-errors.md` if the API returns non-200") rather than a generic "see references/" ([progressive disclosure](https://agentskills.io/skill-creation/best-practices#structure-large-skills-with-progressive-disclosure), [spec progressive disclosure](https://agentskills.io/specification#progressive-disclosure)). Reference bundled files with **relative paths from the skill root**, keep references **one level deep** (no nested chains), and keep individual reference files focused so on-demand loads stay small ([file references](https://agentskills.io/specification#file-references), [references dir](https://agentskills.io/specification#references)). Same relative-to-skill-root convention applies inside support files ([referencing scripts](https://agentskills.io/skill-creation/using-scripts#referencing-scripts-from-skillmd)).

**Why it matters.** Once activated, the whole `SKILL.md` body occupies context alongside conversation, system context, and other skills; every token competes for attention. Conditional loads keep the upfront cost low and fetch detail only when the trigger condition holds ([spending context wisely](https://agentskills.io/skill-creation/best-practices#spending-context-wisely)).

**[Researcher's observation.]** The 4 bodies are lean (~30 lines each) so nothing currently needs splitting; references are one level deep (`assets/…`, `templates/…`, `scripts/…`). Two notes: (a) there is no `references/` dir — long input/output examples live in `examples/` and schemas in `assets/`, which is spec-compatible ("any additional files") but means conditional-load triggers ("read X when Y") are implicit rather than stated; (b) bodies invoke `scripts/*.mjs` while the source tree holds `scripts/*.ts` — consistent with the per-skill bundled `dist/` output (which runs `node scripts/<name>.mjs`), but the mapping is unstated in the bodies and could confuse an agent working from source.

## 5. Length budgets and scope

**Rule.** Keep `SKILL.md` under **500 lines and 5,000 tokens** ([progressive disclosure](https://agentskills.io/specification#progressive-disclosure), [structuring large skills](https://agentskills.io/skill-creation/best-practices#structure-large-skills-with-progressive-disclosure)). Scope each skill as one **coherent unit of work** (like a function): too narrow forces multi-skill loads with overhead/conflicts; too broad won't activate precisely — e.g. query-plus-format may cohere, while adding administration overreaches ([design coherent units](https://agentskills.io/skill-creation/best-practices#design-coherent-units)). Aim for **moderate detail**: concise stepwise guidance + a working example beats exhaustive edge-case coverage; let agent judgment handle the long tail ([aim for moderate detail](https://agentskills.io/skill-creation/best-practices#aim-for-moderate-detail)). Cut anything the agent already knows — the test is "would the agent get this wrong without this instruction?"; if unsure, test, and if the agent handles the task well with no skill, the skill adds no value ([add/omit](https://agentskills.io/skill-creation/best-practices#add-what-the-agent-lacks-omit-what-it-knows)).

**Why it matters.** Over-comprehensive skills degrade performance: the agent struggles to extract what's relevant and pursues unproductive paths triggered by inapplicable instructions ([moderate detail](https://agentskills.io/skill-creation/best-practices#aim-for-moderate-detail)).

**[Researcher's observation.]** All 4 bodies are ~30–33 lines — far inside budget, coherently scoped to one pipeline stage each with explicit entry/exit conditions and hand-offs. No body explains general concepts (no "what is OKLCH/DTCG/Style Dictionary" primers); content is project-specific conventions and commands, i.e. exactly the "what the agent lacks" slice.

## 6. Scripts, resources, and examples conventions

**Rule.** Spec layout: `scripts/` = executable code (self-contained or with documented deps, helpful errors, graceful edge cases); `references/` = on-demand docs (`REFERENCE.md`, `FORMS.md`, domain files); `assets/` = static resources (templates, images, data/lookup files) ([optional directories](https://agentskills.io/specification#optional-directories), [scripts](https://agentskills.io/specification#scripts), [references](https://agentskills.io/specification#references), [assets](https://agentskills.io/specification#assets)). List available scripts in `SKILL.md` and instruct the agent to run them via relative-path code blocks ([referencing scripts](https://agentskills.io/skill-creation/using-scripts#referencing-scripts-from-skillmd)). Prefer one-off runner commands (`npx`, `uvx`) with **pinned versions** for existing tools, and state prerequisites in `SKILL.md`/`compatibility` rather than assuming the environment; promote complex commands into tested `scripts/` ([one-off commands](https://agentskills.io/skill-creation/using-scripts#one-off-commands)). Bundle reusable logic as **self-contained scripts** with inline deps (PEP 723, Deno `npm:`/`jsr:`, Bun auto-install) when traces show the agent reinventing the same logic each run ([self-contained scripts](https://agentskills.io/skill-creation/using-scripts#self-contained-scripts), [bundling reusable scripts](https://agentskills.io/skill-creation/best-practices#bundling-reusable-scripts)). Scripts for agents must: take **no interactive prompts** (flags/env/stdin only, with clear `--help`); emit **helpful errors** (what failed, what was expected, what to try); prefer **structured output** (JSON/CSV) with data on stdout and diagnostics on stderr; be **idempotent**, reject ambiguous input, offer `--dry-run` for destructive ops, use **meaningful exit codes**, safe defaults for destructive actions, and bounded/paginated output ([designing for agentic use](https://agentskills.io/skill-creation/using-scripts#designing-scripts-for-agentic-use), [further considerations](https://agentskills.io/skill-creation/using-scripts#further-considerations)).

**Why it matters.** The agent reads stdout/stderr to decide its next step, so error quality directly shapes recovery; non-interactive shells hang on prompts; structured stdout stays composable with `jq`/`cut` pipelines; retries are normal, so non-idempotent scripts corrupt state ([same](https://agentskills.io/skill-creation/using-scripts#designing-scripts-for-agentic-use)).

**[Researcher's observation.]** Each skill lists and invokes its script (`generate.mjs`, `audit.mjs`, `build.mjs`) with exact flags — matching the list-then-invoke convention; token-audit's binary exit-code gate plus "never lower `--min-ratio` unasked" matches meaningful-exit-codes + safe-defaults guidance. Gaps vs the guide: no `--help` output is documented in the bodies, `--dry-run`/idempotency aren't stated (token-math does warn to ask before `--force`, which is the safe-default spirit), and output structuredness (JSON report shapes) is shown only via `examples/` files rather than declared.

## 7. Instruction patterns: gotchas, templates, checklists, validation loops

**Rule.** The docs prescribe four reusable patterns, used only where they fit: (a) **Gotchas sections** — the highest-value content in many skills: concrete environment-specific corrections ("`users` uses soft deletes, always add `WHERE deleted_at IS NULL`"), kept in `SKILL.md` so they're read before the situation arises; every agent mistake you correct should be appended here ([gotchas](https://agentskills.io/skill-creation/best-practices#gotchas-sections)). (b) **Output templates** — concrete structures beat prose descriptions; short ones inline, longer/conditional ones in `assets/` referenced from `SKILL.md` ([templates](https://agentskills.io/skill-creation/best-practices#templates-for-output-format)). (c) **Checklists** for multi-step workflows with dependencies/validation gates ([checklists](https://agentskills.io/skill-creation/best-practices#checklists-for-multi-step-workflows)). (d) **Validation loops** — do work → run validator → fix → repeat until pass — and **plan-validate-execute** for batch/destructive ops, where the plan is validated against a source of truth before execution ([validation loops](https://agentskills.io/skill-creation/best-practices#validation-loops), [plan-validate-execute](https://agentskills.io/skill-creation/best-practices#plan-validate-execute)). Calibrate prescriptiveness to fragility: freedom + _why_ where variation is safe; exact sequences where it isn't; and **defaults, not menus** — pick a default, mention alternatives briefly ([calibrating control](https://agentskills.io/skill-creation/best-practices#calibrating-control), [specificity](https://agentskills.io/skill-creation/best-practices#match-specificity-to-fragility), [defaults](https://agentskills.io/skill-creation/best-practices#provide-defaults-not-menus)).

**Why it matters.** Gotchas pre-empt the exact mistakes agents otherwise repeat; templates exploit agents' pattern-matching; checklists prevent skipped steps; validators give the agent self-correction signal without a human turn; rationale-backed freedom yields better context-dependent decisions than rigid directives ([same sections](https://agentskills.io/skill-creation/best-practices#patterns-for-effective-instructions)).

**[Researcher's observation.]** All 4 skills use per-step "Done when" gates (checklist + validation-loop spirit) and state defaults with escape hatches (typography/density defaults, `--min-ratio 4.5` with a no-softening rule, `--force` ask-first). Gotcha-style lines exist (neutral chroma 0.008–0.015, anchor `l` 0.45–0.65, hex-means-bypassed-transform, alias dotted-from-root) but are inline in steps rather than a labelled Gotchas section; output templates live as `examples/` + `templates/` files referenced by name, matching the assets-referenced pattern.

## 8. Grounding and iteration: from real expertise, refined by execution

**Rule.** Never generate a skill from LLM general knowledge alone — that yields vague generic procedures. Ground in real expertise via hands-on task extraction (steps that worked, corrections made, I/O formats, context supplied) or synthesis from project artifacts (runbooks, schemas, review comments, history, failure cases) ([start from expertise](https://agentskills.io/skill-creation/best-practices#start-from-real-expertise)). Then **refine with real execution**: run against real tasks, feed all results back, ask about false positives/misses/cuts; read **execution traces**, not just outputs — wasted steps signal vague, inapplicable, or option-heavy instructions ([refine](https://agentskills.io/skill-creation/best-practices#refine-with-real-execution)). The structured form is eval-driven iteration: 2–3 realistic test cases (varied phrasing, edge cases, real context) in `evals/evals.json`, with-skill vs without-skill (or old-version) runs in clean contexts, timing capture, assertions added after first outputs, evidence-graded PASS/FAIL, benchmark aggregation, pattern analysis, human review, and repeat until feedback is empty or gains plateau ([designing test cases](https://agentskills.io/skill-creation/evaluating-skills#designing-test-cases), [running evals](https://agentskills.io/skill-creation/evaluating-skills#running-evals), [grading](https://agentskills.io/skill-creation/evaluating-skills#grading-outputs), [iterating](https://agentskills.io/skill-creation/evaluating-skills#iterating-on-the-skill)).

**Why it matters.** First drafts are usually wrong in scope or calibration; only execution reveals false triggers, missed cases, and dead weight, and the with/without delta proves the skill earns its context cost ([aggregating results](https://agentskills.io/skill-creation/evaluating-skills#aggregating-results), [analyzing patterns](https://agentskills.io/skill-creation/evaluating-skills#analyzing-patterns)).

**[Researcher's observation.]** The 4 skills read as grounded (exact flags, measured thresholds, named failure modes) rather than generic — consistent with artifact-synthesised skills. The missing piece is any recorded execute-then-revise loop: no `evals/` dirs, no trigger-rate tests, no benchmark files exist under `src/skills/` at observation time.

## 9. Description testing and trigger-eval method

**Rule.** Build ~20 realistic eval queries (8–10 should-trigger varying phrasing/explicitness/detail/complexity, 8–10 should-not-trigger as **near-misses** sharing keywords but needing something else, with real paths/context/typos), run each ~3 times, compute trigger rates against a 0.5 threshold; split train (~60%) / validation (~40%) to avoid overfitting, iterate ≤5 rounds generalising (not keyword-patching) under the 1024-char cap, select by validation pass rate, then sanity-check on 5–10 fresh queries ([designing trigger evals](https://agentskills.io/skill-creation/optimizing-descriptions#designing-trigger-eval-queries), [testing](https://agentskills.io/skill-creation/optimizing-descriptions#testing-whether-a-description-triggers), [train/validation splits](https://agentskills.io/skill-creation/optimizing-descriptions#avoiding-overfitting-with-trainvalidation-splits), [optimization loop](https://agentskills.io/skill-creation/optimizing-descriptions#the-optimization-loop), [applying](https://agentskills.io/skill-creation/optimizing-descriptions#applying-the-result)). The `skill-creator` skill automates the loop ([same](https://agentskills.io/skill-creation/optimizing-descriptions#the-optimization-loop)).

**Why it matters.** Model triggering is nondeterministic, so single runs mislead; and optimising against the full query set overfits wording that fails on fresh prompts — the split plus fresh-query check is what proves generalisation ([same](https://agentskills.io/skill-creation/optimizing-descriptions#avoiding-overfitting-with-trainvalidation-splits)).

**[Researcher's observation.]** No trigger-eval query sets exist for the 4 skills at observation time. Pipeline-ordered descriptions ("First… Second… Third… Final stage") give each skill distinctive trigger vocabulary, which should help near-miss discrimination, but the adjacent-skill boundaries (token-math vs token-build, token-audit vs token-build) are exactly the near-miss cases a future eval set should probe.

## 10. Common anti-patterns called out by the docs

Each anti-pattern below is named in the official docs; the fix points to the section above.

- **LLM-generated generic skill** ("handle errors appropriately", "follow auth best practices") with no domain specifics — ground in real tasks/artifacts instead ([pitfall](https://agentskills.io/skill-creation/best-practices#start-from-real-expertise)). **[Observation:]** not present in our 4 skills; content is specific throughout.
- **Explaining what the agent already knows** (what a PDF/HTTP/migration is) — cut unless the agent would get it wrong without the line ([add/omit with PDF example](https://agentskills.io/skill-creation/best-practices#add-what-the-agent-lacks-omit-what-it-knows)). **[Observation:]** not present; no primers detected.
- **Exhaustive edge-case coverage** that buries the relevant path — prefer concise stepwise guidance + working example ([moderate detail](https://agentskills.io/skill-creation/best-practices#aim-for-moderate-detail)). **[Observation:]** not present; bodies are minimal.
- **Menus without a default** ("You can use pypdf, pdfplumber, PyMuPDF…") — pick a default with an escape hatch ([defaults](https://agentskills.io/skill-creation/best-practices#provide-defaults-not-menus)). **[Observation:]** not present; each decision point names a default.
- **Instance-specific instructions** posing as a method — generalise the approach ([procedures](https://agentskills.io/skill-creation/best-practices#favor-procedures-over-declarations)). **[Observation:]** not present.
- **Bloated SKILL.md that should have been split** with conditional loads — move reference to separate files with explicit when-to-load triggers ([progressive disclosure](https://agentskills.io/skill-creation/best-practices#structure-large-skills-with-progressive-disclosure)). **[Observation:]** not currently an issue at ~30 lines each; revisit if bodies grow.
- **Vague/option-heavy instructions** found via wasted trace steps; **inapplicable instructions** the agent follows anyway — tighten, scope, or remove ([refine tip](https://agentskills.io/skill-creation/best-practices#refine-with-real-execution)). **[Observation:]** no traces reviewed; unknown until evals run.
- **Vague description** ("Process CSV files" / "Helps with PDFs") and **implementation-focused description** instead of user intent ([poor example](https://agentskills.io/specification#description-field), [writing descriptions](https://agentskills.io/skill-creation/optimizing-descriptions#writing-effective-descriptions)). **[Observation:]** not present; descriptions are intent-focused.
- **Unpinned one-off commands** and **assumed prerequisites** — pin versions, declare requirements in `compatibility`/body ([one-off tips](https://agentskills.io/skill-creation/using-scripts#one-off-commands)). **[Observation:]** partially present: `compatibility: Node.js >=22.12` is declared, but bodies pin no tool versions (Style Dictionary is bundled programmatically, so this is low-risk; still unstated).
- **Interactive scripts, opaque errors, free-text stdout, non-idempotent or ambiguous-input-guessing scripts** ([agentic-use requirements](https://agentskills.io/skill-creation/using-scripts#designing-scripts-for-agentic-use)). **[Observation:]** not verified from SKILL.md alone; needs a script audit against `--help`/error/exit-code/stdout criteria.
- **Overfitting descriptions to test queries** (keyword-patching) and **judging by single runs** — use train/validation split, 3 runs, fresh-query check ([overfitting](https://agentskills.io/skill-creation/optimizing-descriptions#avoiding-overfitting-with-trainvalidation-splits)). **[Observation:]** no evals exist yet, so neither practised nor violated.
