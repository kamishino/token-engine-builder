# Skills architecture comparison: Matt Pocock vs Stitch, reflected against token-engine-builder

Comparison of the two in-repo research notes, reflected against this repo's own architecture doc. Observations only — no action plan.

## 2. Reflection against ARCHITECTURE.md

References below to our architecture are to [../../ARCHITECTURE.md](../../ARCHITECTURE.md) unless noted.

### PROS — what our architecture does better, and why

- **Standalone executables via per-skill bundling.** One Vite pass per skill with shared code inlined means a copied `dist/<skill>/` folder runs with `node scripts/<name>.mjs` and no install ([../../ARCHITECTURE.md](../../ARCHITECTURE.md), §§1, 4). Both compared repos ship source and resolve dependencies at use time — Pocock has effectively no executable layer beyond one template script ([matt-pocock-skills-architecture.md](./matt-pocock-skills-architecture.md), §3); Stitch requires the MCP server plus per-skill extras (`npm install`, `npx tsx`, `puppeteer`) connected at run time ([stitch-skills-architecture.md](./stitch-skills-architecture.md), §3). Our decision trades build complexity for zero run-time prerequisites.
- **Documented build decisions that each fixed a real failure.** The three load-bearing decisions (per-skill passes vs shared chunks; SSR/Node conditions vs the SD browser-memfs shim; in-process token merge vs the unre-bundlable glob loader) each name the failure they fixed ([../../ARCHITECTURE.md](../../ARCHITECTURE.md), §4). Neither compared repo documents equivalent build rationale — Pocock has no build step at all ([matt-pocock-skills-architecture.md](./matt-pocock-skills-architecture.md), §1), and Stitch's build-adjacent surface is a static `1.0.0` with no release machinery ([stitch-skills-architecture.md](./stitch-skills-architecture.md), §5).
- **Measured verification gate.** Our smoke run asserts concrete outputs (anchor exactly on `brand.500`, 7-pair/2-theme audit ratios 5.21–17.09, 42 `oklch()` values per dark file, 4dp rem rounding, kebab-case Tailwind namespaces, stylelint-clean CSS) ([../../ARCHITECTURE.md](../../ARCHITECTURE.md), §5). Stitch CI checks only syntactic/AST validity of two gold-standard examples with no measured gate ([stitch-skills-architecture.md](./stitch-skills-architecture.md), §5); the Pocock note records no automated skill verification at all ([matt-pocock-skills-architecture.md](./matt-pocock-skills-architecture.md), §§3, 5).
- **Enforced token discipline in code, not just convention.** Tier rules (raw values only in Tier 1; alias-only above), 7-pair WCAG gate at 4.5 default with a negative `--min-ratio 21` probe, alias-resolution/cycle checks, and zero-raw-above-Tier-1 enforcement all live in the pipeline ([../../ARCHITECTURE.md](../../ARCHITECTURE.md), §3). The closest upstream parallels are advisory or partial: Stitch's hex-gate plus per-project `style-guide.json` re-extraction ([stitch-skills-architecture.md](./stitch-skills-architecture.md), §3 comparison) and its `verify-setup.sh` which prints fix suggestions rather than failing closed ([stitch-skills-architecture.md](./stitch-skills-architecture.md), §3).
- **Spec-clean skill names.** Our skill directories and names are plain kebab-case matching their directories, consistent with the directory-matching rule both notes attribute to the spec ([matt-pocock-skills-architecture.md](./matt-pocock-skills-architecture.md), §2; [stitch-skills-architecture.md](./stitch-skills-architecture.md), §2). Stitch's `stitch::` family deviates from both the charset and directory-match rules and needs renaming on at least one harness ([stitch-skills-architecture.md](./stitch-skills-architecture.md), §2).
- **Typed module contracts.** `src/shared/` assigns each module an owned surface with key exports (DTCG types, OKLCH engine, scales, SD builder, portable paths) ([../../ARCHITECTURE.md](../../ARCHITECTURE.md), §2). The Pocock note shows cross-skill sharing done purely by Skill-tool invocation with no shared-code layer ([matt-pocock-skills-architecture.md](./matt-pocock-skills-architecture.md), §§1, 6 comparison); the Stitch note shows per-skill scripts plus run-time delegation, likewise with no shared module contracts ([stitch-skills-architecture.md](./stitch-skills-architecture.md), §§1, 3).

### CONS — genuine weaknesses or risks the comparison exposes

- **No distribution channel beyond filesystem copy.** Our install story is copying `dist/<skill>/` into a skills directory, with no manifest, marketplace, or update channel — a divergence both notes record against upstream plugin/marketplace manifests and installer CLIs ([matt-pocock-skills-architecture.md](./matt-pocock-skills-architecture.md), §6 comparison; [stitch-skills-architecture.md](./stitch-skills-architecture.md), §6 comparison). Consumers therefore have no managed-update path; every update is a manual re-copy.
- **Flat skill set with no grouping or promotion semantics.** `src/skills/` holds four pipeline skills with no bucket/plugin/promotion layer ([../../ARCHITECTURE.md](../../ARCHITECTURE.md), §1), while Pocock sorts skills into five buckets with two promoted and enforces the distinction in index, manifest, and docs ([matt-pocock-skills-architecture.md](./matt-pocock-skills-architecture.md), §1), and Stitch sorts 15 skills into three versioned plugins ([stitch-skills-architecture.md](./stitch-skills-architecture.md), §1). As the skill count grows, the absence of a grouping story is the gap both taxonomies highlight.
- **No invocation/permission metadata.** Upstream skills declare who may invoke them and what tools they may use — Pocock via `disable-model-invocation` + `agents/openai.yaml` policy with description semantics keyed off it ([matt-pocock-skills-architecture.md](./matt-pocock-skills-architecture.md), §2), Stitch via `allowed-tools` with MCP wildcards on every skill ([stitch-skills-architecture.md](./stitch-skills-architecture.md), §2). Our skills carry neither marker ([matt-pocock-skills-architecture.md](./matt-pocock-skills-architecture.md), §6 comparison; [stitch-skills-architecture.md](./stitch-skills-architecture.md), §6 comparison), so harness-side invocation control and tool scoping are unexpressed.
- **No per-skill docs/index registration discipline.** Pocock requires README entries, bucket README entries, docs pages for promoted skills, and router re-sync on skill changes ([matt-pocock-skills-architecture.md](./matt-pocock-skills-architecture.md), §§1, 6 comparison); Stitch ships per-skill READMEs on build skills plus plugin tables with prompt examples ([stitch-skills-architecture.md](./stitch-skills-architecture.md), §1). Our repo has no equivalent registration checklist, so skill additions can land without index or docs updates.
- **Orchestration is file-pipeline only.** Our skills chain by passing artifacts through files (`style-spec.json` → `tokens/` → gate → CSS) ([stitch-skills-architecture.md](./stitch-skills-architecture.md), §6 comparison), with no run-time skill-to-skill delegation equivalent to Pocock's Skill-tool chaining ([matt-pocock-skills-architecture.md](./matt-pocock-skills-architecture.md), §1) or Stitch's `code-to-design` sequencing ([stitch-skills-architecture.md](./stitch-skills-architecture.md), §1). Multi-skill agent workflows therefore have no named pattern in our architecture.
- **Smoke-only verification with no CI workflow.** Our verification gate is explicitly "smoke, not tests" with no test suite ([../../ARCHITECTURE.md](../../ARCHITECTURE.md), §5). The comparison shows even minimal CI has value Stitch captures and we do not: a push/PR workflow validating checked-in artifacts ([stitch-skills-architecture.md](./stitch-skills-architecture.md), §5). Our smoke assertions are stronger per-run but have no automation binding them to changes.
- **Version story weaker than Pocock's.** Our package is `private: true` at `0.1.0` with changeset tooling present (per the Stitch note's comparison, [stitch-skills-architecture.md](./stitch-skills-architecture.md), §6 comparison) but no per-change versioning discipline comparable to Pocock's changeset-per-change + generated changelog + version-gated managed updates ([matt-pocock-skills-architecture.md](./matt-pocock-skills-architecture.md), §5). Against Stitch's static `1.0.0`/no-machinery we compare evenly, not favorably.
