# Agent usage scenarios, iteration protocol, DESIGN.md ingestion, essential devDeps

Research answering three questions for the five-skill DTCG token pipeline, from primary sources on 2026-10-19: (1) in what scenarios users ask an agent to use these skills, and how the agent iterates correctly across foundation-only change rounds without producing hand-authored "AI slop"; (2) whether the skills can ingest a pasted DESIGN.md (Stitch format) or an internet prompt and add the missing tokens; (3) the essential devDependency set for a consumer project, and which parts the skills already absorb. The DESIGN.md format anatomy is not re-derived here; it is taken from [design-md-vs-design-system.md](./design-md-vs-design-system.md) §1.

Conventions: repo citations give `path:line` in this repository. Upstream claims cite official docs/repos by URL. Statements labelled **[proposal]** are this note's design, not existing behaviour.

## 2. The iteration protocol

### 2.1 One edit surface: `style-spec.json`

Across foundation-change rounds (colour, typography, spacing, radii, density, themes), the agent edits **`style-spec.json` only**. It is the recorded-decision contract between `token-style` and `token-math` (`src/shared/types.ts:76-106`). Field per dimension:

### 2.2 Per-round loop

1. **Read back before touching anything.** Re-read `style-spec.json` from disk (not from conversation memory), and state the current palette/cluster/defaults. This mirrors the creation-time rules: if a spec already exists, show the current palette/cluster and ask before overwriting (`src/skills/token-style/SKILL.md:28`); unanswered interview questions become stated-aloud defaults, not silent ones (`src/skills/token-style/SKILL.md:17`); every vibe adjustment is "stated aloud with its reason" (`src/skills/token-style/references/design-mappings.md:34`).
2. **Edit the spec — the smallest field set that expresses the request** (§2.1). Colour judgement (new anchors, renames) goes through `token-style` steps 3–5 (propose → read back → record) (`src/skills/token-style/SKILL.md:25-29`); mechanical fields (density, spacing base, radii, type ratio) can be edited directly, still stated aloud.
3. **Preview, then generate with `--force` — after asking.** `node ./scripts/generate.mjs --spec style-spec.json --out tokens --dry-run` prints what would be written plus the provenance status (`generate.ts:126-143`). Real run: same command with `--force` instead of `--dry-run`; `token-math` requires asking before `--force` (`src/skills/token-math/SKILL.md:21`).
   Guard semantics the agent must understand rather than fight (`src/shared/guard.ts:4-9,77-103`; `generate.ts:151-168`):
   - Any existing `tokens/` without `--force` → refusal ("output exists … pass --force").
   - Manifest present and **tampered or unreadable** (a generated file changed or missing) → refusal listing `changed:`/`missing:` paths, even before the generic output-exists check; `--force` logs "overwriting hand-edited tokens (--force)" and proceeds.
   - Manifest **absent** with `--force` → the existing tree is "adopted" and a manifest is created.
   - Extra user files (`added`) never block and survive generation.
   - Output dirs equal to/ancestral to cwd or the home dir are refused (`guard.ts:111-119`, applied at `generate.ts:145-149`).
     On success, `generate` rewrites the manifest with `inputHash` = SHA-256 of the spec file (`generate.ts:403-409`) — this hash is the round's fingerprint.
4. **Audit the exact regenerated tree.** `node ./scripts/audit.mjs --tokens tokens --min-ratio 4.5` (add `--min-apca` only if the user changed it). Done when per-theme PASS/FAIL lines and an exit code print (`src/skills/token-audit/SKILL.md:21-22`). Audit also verifies the tokens provenance manifest when present, and a tampered/unreadable manifest fails the run regardless of contrast (`src/skills/token-audit/scripts/audit.ts:246-251`).
5. **Remediate by the ladder, max 3 loops** (`src/skills/token-audit/references/contrast.md:24-28`; `src/skills/token-audit/SKILL.md:24-28`):
   1. Move the offending semantic alias one step further from its background (`neutral.700` → `neutral.800`).
   2. Only if step-moves can't fix it: shift the anchor `l` in `style-spec.json` by ≥0.05 and re-run `token-math` (back to step 3).
   3. After 3 loops, escalate with the failing pairs table. Lowering `--min-ratio`/`--min-apca` is the user's call, never a remediation.

   ⚠️ Durability caveat (verified, see §2.4 gap G2): rung 1 edits a file `generate` rewrites, so it does not survive the next round; rung 2 is the only rung that persists.

6. **Build only on a passing tree.** Entry condition: "audit exits 0 on this exact tree" (`src/skills/token-build/SKILL.md:11`). Build each needed theme/profile (§1 rows 4a, 6), then spot-check outputs: `tokens.css` contains `oklch(`, `theme.css` contains `--color-` inside `@theme`, `components.md` has `## button` + a `focus-ring` row, `DESIGN.md` frontmatter `colors.primary` equals the hex of the spec's primary anchor when `--spec` was passed (`src/skills/token-build/SKILL.md:26-27`).
7. **Report the diff of the round**, not just success: spec fields changed (old → new, with the reason), the new manifest `inputHash`, which themes/ramp steps moved, audit ratios before/after for affected pairs, and the rebuilt file paths + import lines (`src/skills/token-build/SKILL.md:28-29`). The read-back habit (step 1) plus this diff is what prevents drift across rounds: the spec on disk, re-read and re-stated, is the shared memory — the conversation is not.

## 3. DESIGN.md / prompt ingestion assessment

Format anatomy per [design-md-vs-design-system.md](./design-md-vs-design-system.md) §1: YAML frontmatter with `colors {primary, secondary}`, `typography {fontSans, scale}`, `rounded {sm, md, lg}` (px strings), `spacing {base, density}`, a `components` name list, then eight normative prose sections. That note's verdict — DESIGN.md is a derived export, never the source of truth — stands; the question here is narrower: can a _foreign_ DESIGN.md or prompt serve as **evidence** into `token-extract`, the way that note already contemplates ("A foreign DESIGN.md could be one more scan source for candidate anchors — evidence, ranked like any other, still subject to read-back", §3)?

### 3.1 Current state (verified in code)

- **Markdown is not scanned.** `SCAN_EXTS = {'.css','.scss','.json','.ts','.tsx','.js','.jsx','.html'}` (`src/skills/token-extract/scripts/extract.ts:40`); scan is recursive, sorted, skipping `node_modules/.git/dist/release/coverage/.next` (`extract.ts:39`; `heuristics.md:7`). A pasted `DESIGN.md` in the project root is invisible to the extractor today.
- **What the named-colour regex _would_ catch if `.md` were added** (`extract.ts:60-62`): `NAMED_COLOR` matches `name: "#hex" | 'oklch(...)' | rgb(a)(...)` and `BARE_COLOR` matches any bare hex/oklch literal anywhere in the text.
  - Stitch frontmatter in flow style, `colors: {primary: "#3B82F6", secondary: "#F59E0B"}` → **caught**, with names `primary`/`secondary`. `primary` scores +60 in `nameScore` (`extract.ts:68-74`); `secondary` scores 0 from the name but still competes on chroma/lightness (`extract.ts:85-88`).
  - Block-style YAML (`primary:` on its own line, value quoted) → also caught: the regex allows optional quotes around name and value (`extract.ts:60-61`).
  - The **prose sections'** hex/`var(--…)` mentions (anatomy §1 of the sibling note) → bare literals caught by `BARE_COLOR` with no name (score from chroma/lightness only). `var(--brand-500)` references contain no literal → not caught.
  - **Not caught:** `typography.fontSans` (the font regex requires the literal `font-family:` (`extract.ts:112`)); `rounded.*` px values (radius regex requires the literal `border-radius: Npx` (`extract.ts:117`)); `spacing.base/density`; colour **names in words** ("cerulean", "warm sand") — the regexes require a hex/oklch/rgb literal adjacent to the name. English colour names alone are invisible.
  - Even the colours that are caught collapse: only the **top-ranked** candidate becomes the anchor; ranks 2–5 are printed as evidence but the recorded palette is top-anchor + **analogous-derived** secondary/accent, ignoring the source's own secondary (`extract.ts:125-139,185-197`). So naive ".md in SCAN_EXTS" would extract _a_ colour and discard the document's actual palette structure.
- **Prompt text (chat-pasted, no file)** has no ingestion path at all today: `token-style`'s interview can accept "named color, existing hex, or 'you choose'" and convert to OKLCH (`src/skills/token-style/SKILL.md:19`), but that is the agent improvising in conversation — no ranking, no evidence record.

### 3.2 Feasibility design **[proposal]**

Extend `token-extract` with a dedicated DESIGN.md frontmatter parser; do **not** merely add `.md` to `SCAN_EXTS` (per §3.1, that mis-ranks prose hexes against frontmatter and drops the palette).

1. **Detect & parse.** A `.md` file whose opening `---…---` block contains a `colors:` key is a DESIGN.md candidate. Parse only the frontmatter maps named in the sibling note §1 (`colors`, `typography`, `rounded`, `spacing`, `components`) with a small flat-map parser (the frontmatter shape is flat `key: value` pairs, per the kamiflow template cited there) — no new dependency (see §4: skills must stay install-free).
2. **Map to a candidate spec:**
   | Frontmatter                                                | Spec field                                        | Rule                                                                                                                                                                                                                                                                                                                                          |
   | ---------------------------------------------------------- | ------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
   | `colors.primary`                                           | `palette[0]` `{role:"primary"}`                   | Parse hex/oklch via the existing `parseToOklch` (`extract.ts:76-82`); unparseable → skip + evidence line.                                                                                                                                                                                                                                     |
   | `colors.secondary`, `colors.accent`, other `colors.*` keys | `palette[1..]` roles `secondary`/`accent`/`other` | Preserves the source palette — the key improvement over today's analogous derivation. If total colours < 3, `generate` will reject the spec (3–5 enforced, `generate.ts:57-60`), so top up with `buildHarmony(anchor,'analogous')` exactly as extract already does (`extract.ts:185`), and mark topped-up entries as derived in the evidence. |
   | (each colour)                                              | `palette[].name`                                  | Slug per `color-naming.md` rules (hue sector → name family, unique, no numbers) — frontmatter keys are roles, not names, and roles must not become slugs (`color-naming.md:10`).                                                                                                                                                              |
   | `colors.primary` anchor                                    | `cluster` (check, not choice)                     | Find the cluster whose hue/chroma/lightness box contains the anchor (`style-clusters.md:7-24`); record it if exactly the box matches, flag "weak/out-of-cluster" at read-back if none — mirroring extract's existing instruction to resolve and record the cluster (`src/skills/token-extract/SKILL.md:24`).                                  |
   | `typography.fontSans`                                      | `typography.fontFamily`                           | Direct string; `typography.scale` maps to `baseSizePx`/`ratio` **only if** numeric values parse, otherwise stated defaults (16px, 1.25 — `extract.ts:201-205`).                                                                                                                                                                               |
   | `rounded {sm,md,lg}` px strings                            | `radius {sm,md,lg}`, `full: 9999`                 | Strip `px`, numeric → spec numbers (`types.ts:104`).                                                                                                                                                                                                                                                                                          |
   | `spacing.base` / `spacing.density`                         | `spacingBasePx` / `density`                       | Base only if px-numeric; density only if exactly `comfortable`/`compact` (`types.ts:103`), else stated default.                                                                                                                                                                                                                               |
   | `neutralHue`/`neutralChroma`                               | derived                                           | From the primary anchor (hue = anchor hue, chroma 0.012), as extract already does (`extract.ts:199-200`).                                                                                                                                                                                                                                     |
   | `components` name list                                     | **ignored, noted**                                | There is no spec field for components; component tokens are fixed templates (button/card/input, §3.3). Print the list as an evidence line ("components noted, not imported: …") so nothing is silently dropped.                                                                                                                               |
   | `name`/`description`, prose sections                       | `name`; prose ignored                             | Prose hexes stay unscanned for ranking (frontmatter outranks prose by construction); guide prose could optionally seed `guide.overview` (`types.ts:97-101`) — optional, off by default.                                                                                                                                                       |
3. **Evidence & read-back unchanged.** The parser feeds the same candidate+evidence output and the same `token-style` read-back (confirm / veto to another candidate / override) (`src/skills/token-extract/SKILL.md:24-25`). DESIGN.md colours enter as _claims to be read back_, consistent with the sibling note's "its colors are claims, not values under test" (§1) — the audit gate remains the first measured check.
4. **Prose prompts (no file).** **[proposal]** Rank signals by evidence strength, lowest-confidence last:
   1. `role: #hex` / `role: oklch(...)` labelled literals (same shape as `NAMED_COLOR`, `extract.ts:60-61`) — highest; the label supplies the role.
   2. Bare hex/oklch literals — anchor candidates, ranked by the existing chroma/lightness heuristics (`extract.ts:85-88`).
   3. Colour **names in words** ("cerulean", "sage") — lowest confidence. `color-naming.md` maps anchor → name, not name → anchor; reversing it yields a hue-sector _range_, not a value. The agent may propose the sector centre (sectors at `color-naming.md:15-28`) as a candidate anchor, must label it name-derived at read-back, and must expect the user to adjust — exactly the treatment vague adjectives already get via clusters (`style-clusters.md:28`).
      An internet prompt has no provenance beyond the paste; the spec's read-back is the only verification, and the note should say so wherever this path is documented.

### 3.3 "Add the missing tokens" already works by construction

Given any confirmed candidate spec, `generate` synthesises the full 3-tier tree; the source only has to supply what is genuinely creative:

| Must come from the source (DESIGN.md / prompt / interview)                                                | Synthesised by `generate`                                                                                                                                                                                                                                                                                                                                                                                     |
| --------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 3–5 palette anchors with exactly one primary (or 1 anchor + analogous top-up, §3.2) (`generate.ts:57-64`) | A 5/9/11-step OKLCH ramp per palette colour, anchor exactly on step 500 (`generate.ts:208-220`)                                                                                                                                                                                                                                                                                                               |
| Colour names (slugs) (`types.ts:63-68`)                                                                   | Neutral ramp from `neutralHue`/`neutralChroma`; white/black (`generate.ts:212-220`)                                                                                                                                                                                                                                                                                                                           |
| Font family (if fidelity matters) (`types.ts:90`)                                                         | Feedback ramps for success/warning/danger/info/help from fixed bounded anchors (`src/shared/colors.ts:235-248`; `generate.ts:221-226`)                                                                                                                                                                                                                                                                        |
| Radii, spacing base, density, type base/ratio (else stated defaults) (`types.ts:89-105`)                  | All three semantic themes (light/dark/high-contrast alias maps incl. feedback bg/text pairs) (`generate.ts:235-372`)                                                                                                                                                                                                                                                                                          |
| —                                                                                                         | Layout roles (`layout.inset/gap/section/page`) in every theme (`generate.ts:351-370`); modular type scale, paired line-heights, rhythm scale (`generate.ts:374-391`); spacing & radius primitives (`generate.ts:393-401`); template-copied grid/shadow/animation/z-index primitives and button/card/input component tokens (`generate.ts:172-174`; templates under `src/skills/token-math/templates/tokens/`) |

So "ingest DESIGN.md and add the missing tokens" is not a new generation problem — it is only a _parser + mapping_ problem at the extract boundary. Everything downstream (ramps, themes, feedback, layout, grid, rhythm) already exists.

### 3.4 Recommendation

**Yes — extend `token-extract` with a DESIGN.md frontmatter parser; sized small (S).** Scope: one parser function + field mapping in `extract.ts` (§3.2 table), `.md` admitted **only** through that parser (not blanket `SCAN_EXTS`), evidence lines for ignored/noted fields, `heuristics.md` + `token-extract/SKILL.md` wording, and one gold example beside the existing `examples/extraction-report.example.json`. No new dependency, no change to `token-style`/`token-math`, authority direction preserved (spec/tokens remain the source; the document is evidence — sibling note §4). **No** to prose-prompt parsing as a script feature: prompts arrive in conversation, where `token-style`'s interview already handles hex/named-colour input (`src/skills/token-style/SKILL.md:19`); document the §3.2 confidence ranking as interview guidance instead of code. Rationale for doing it at all: §3.1 shows the current extractor would extract the _wrong thing_ from the one document format design AIs already emit (top hex wins, source palette discarded), while the fix is confined to the one skill whose charter is "evidence, ranked, read back" (`src/skills/token-extract/SKILL.md:11`).

### 4.3 color-names facts and the vendoring question

Facts from the primary source (https://github.com/meodai/color-names, read 2026-10-19):

- **Dataset size:** 31,942 unique colour names ("A meticulously curated collection of **31942** unique color names"; "Color Count: **31942**"), sourced from the single source file `src/colornames.csv` in that repo.
- **Formats:** the full list is published as JSON, JSON.min, CSV, YML, TOON, JS (UMD), XML, HTML, and SCSS; curated subsets exist — "Best of" (hand-picked subset, same format family) and "Short names" (concise names, JSON) — per the repo README's CDN section. The npm package `color-name-list` exposes exports `.`, `./bestof`, and `./short` (`package.json` in that repo: `"name": "color-name-list"`, `"license": "MIT"`).
- **License:** MIT (repo `LICENSE`, "MIT License / Copyright (c) 2017 David Aerne"; package metadata agrees). Vendoring a subset is licence-compatible with attribution.
- Quality mechanics relevant to us: unique names _and_ hex values enforced by CI tests, human curation (AI-generated names discouraged) — README "About" section, same URL.

**Vendoring a subset vs today's agent-knowledge mapping.** Today's mechanism (`color-naming.md:7`): agent knowledge + a 12-sector hue table (sectors at `color-naming.md:15-28`), with slug rules (unique, descriptive, never role/brand) at `color-naming.md:8-11`. Its weakness is creation-moment nondeterminism (gap F8/G8, §2.4): two runs can name the same anchor differently. Its strength is that it costs nothing and the result is frozen in the spec forever after. Vendoring wins **if and when** naming must be reproducible across agents/sessions without a human noticing drift — e.g. if `token-extract` (§3) or programmatic re-naming ever needs a nearest-name function in code. The proportionate move then is the **"Best of"/short curated subset or a sector-representative extract (one name family per hue sector × lightness band), not the full 31,942-entry list**: our naming need is 3–5 slugs per system chosen from known families (`color-naming.md:15-28` already enumerates them), while the full dataset's value (nearest-match over all of sRGB) serves colour-_lookup_ tools, not palette naming. **Verdict: keep agent-knowledge mapping now; vendor a small subset only if/when a script needs deterministic naming.** Revisit trigger: implementing §3.2's automatic slug assignment for ingested DESIGN.md palettes — that code path, unlike the interview, has no human taste step to hide nondeterminism behind.
